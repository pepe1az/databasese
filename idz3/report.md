# Отчёт по выполнению ИДЗ-3
## Репликация в ClickHouse

## 1. Цель работы

Целью лабораторной работы являлось развёртывание ClickHouse-кластера с репликацией, настройка кворума ClickHouse Keeper, создание реплицированной таблицы на движке `ReplicatedMergeTree`, а также проверка отказоустойчивости и консистентности данных между репликами.

## 2. Топология

Для выполнения работы был развёрнут кластер в Docker Compose.

| Компонент | Назначение |
|---|---|
| `clickhouse1` | первая реплика ClickHouse |
| `clickhouse2` | вторая реплика ClickHouse |
| `clickhouse3` | третья реплика ClickHouse |
| `keeper1` | первый узел ClickHouse Keeper |
| `keeper2` | второй узел ClickHouse Keeper |
| `keeper3` | третий узел ClickHouse Keeper |

Используется 1 шард и 3 реплики. ClickHouse Keeper развёрнут отдельными контейнерами, чтобы отказ ClickHouse-узла не был одновременно отказом Keeper-узла. Кворум из трёх Keeper-узлов позволяет пережить потерю одного узла.

## 3. Настройка ClickHouse Keeper

Для проверки Keeper использовались команды:

```bash
echo ruok | nc keeper1 9181
echo mntr | nc keeper1 9181
```

Аналогичные команды были выполнены для `keeper2` и `keeper3`. Результаты сохранены в файл:

```text
checks/keeper_health.txt
```

По результатам проверки Keeper-кворум был работоспособен: один узел выполнял роль leader, остальные — follower.

## 4. Настройка ClickHouse-кластера

В файле `config/clickhouse/cluster.xml` был настроен кластер `clickhouse_cluster`:

- 1 шард;
- 3 реплики;
- подключение к трём Keeper-узлам;
- путь для distributed DDL.

Для каждой реплики были заданы макросы:

- `node1_macros.xml`: `replica1`;
- `node2_macros.xml`: `replica2`;
- `node3_macros.xml`: `replica3`.

## 5. Создание таблицы

Таблица `events` была создана запросом из файла:

```text
sql/01_create_table.sql
```

Используемый движок:

```sql
ENGINE = ReplicatedMergeTree(
    '/clickhouse/tables/{shard}/events',
    '{replica}'
)
```

Таблица была создана на всех трёх репликах через `ON CLUSTER clickhouse_cluster`.

## 6. Проверка репликации

В первую реплику было вставлено 100 000 строк запросом из файла:

```text
sql/02_insert_data.sql
```

После этого данные были прочитаны со всех трёх реплик. Для проверки использовался запрос:

```sql
SELECT
    count() AS rows_count,
    min(event_time) AS min_event_time,
    max(event_time) AS max_event_time,
    uniqExact(user_id) AS unique_users
FROM events;
```

Результаты на всех репликах совпали, что подтверждает корректную репликацию данных.

## 7. Проверка system.replicas

Состояние репликации проверялось запросом из файла:

```text
sql/04_check_replicas.sql
```

Результаты сохранены в файлы:

```text
checks/replicas_status_node1.txt
checks/replicas_status_node2.txt
checks/replicas_status_node3.txt
```

После синхронизации нормальное состояние:

- `total_replicas = 3`;
- `active_replicas = 3`;
- `queue_size = 0`.

## 8. Эксперимент A — потеря одной реплики

Была остановлена третья реплика:

```bash
docker compose stop clickhouse3
```

После этого в первую реплику были вставлены новые данные. Вторая реплика успешно получила данные. Затем третья реплика была запущена обратно:

```bash
docker compose start clickhouse3
```

После восстановления третья реплика догнала очередь репликации. Итоговый вывод сохранён в файл:

```text
checks/experiment_a.txt
```

Также во время синхронизации был сохранён вывод `system.replication_queue`:

```text
checks/replication_queue.txt
```

## 9. Эксперимент B — потеря Keeper-узла

Сначала был остановлен один Keeper-узел:

```bash
docker compose stop keeper3
```

Кворум сохранился, так как два узла из трёх продолжили работу. Вставка данных в таблицу прошла успешно.

Затем был остановлен второй Keeper-узел:

```bash
docker compose stop keeper2
```

После потери большинства Keeper-узлов вставка новых данных стала невозможной. Ошибка была зафиксирована в файле:

```text
checks/experiment_b.txt
```

При этом `SELECT` продолжил работать, потому что чтение выполняется из локальных данных реплики.

## 10. Эксперимент C — конфликт данных

Была остановлена вторая реплика:

```bash
docker compose stop clickhouse2
```

После этого в первую реплику были вставлены данные. Затем вторая реплика была запущена обратно:

```bash
docker compose start clickhouse2
```

После восстановления количество строк на всех репликах совпало. Конфликтов данных не возникло, потому что порядок операций определяется логом репликации в Keeper.

Результаты сохранены в файл:

```text
checks/experiment_c.txt
```

## 11. Вывод

В ходе лабораторной работы был развёрнут ClickHouse-кластер с одной шардой и тремя репликами. Для координации репликации использовался ClickHouse Keeper-кворум из трёх узлов.

Была создана таблица `events` на движке `ReplicatedMergeTree`. После вставки тестовых данных было подтверждено, что данные корректно реплицируются между всеми узлами.

Проведённые эксперименты показали:

- при остановке одной ClickHouse-реплики кластер продолжает принимать данные;
- восстановленная реплика автоматически догоняет актуальное состояние;
- при потере одного Keeper-узла кластер продолжает работать;
- при потере большинства Keeper-узлов запись становится невозможной;
- чтение локальных данных остаётся доступным;
- конфликты данных не возникают, так как репликация выполняется через детерминированный лог Keeper.
