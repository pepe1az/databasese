# Отчёт по ИДЗ-5  
## ManticoreSearch: полнотекстовый поиск и NoSQL-подход

## 1. Цель работы

Целью лабораторной работы было развернуть ManticoreSearch и изучить его применение для полнотекстового поиска по каталогу товаров. В ходе работы рассматривались real-time индексы, морфология, поиск по текстовым полям, фильтрация по атрибутам, JSON-атрибуты, фасетный поиск, а также сравнение ManticoreSearch с PostgreSQL на задаче полнотекстового поиска.

Дополнительно была рассмотрена NoSQL-составляющая ManticoreSearch: возможность хранить документы с набором атрибутов, использовать JSON-поля, а также выполнять операции `UPDATE`, `DELETE` и `REPLACE`.


## 2. Используемые технологии

В работе использовались следующие инструменты:

- ManticoreSearch;
- Docker / Docker Compose;
- MySQL-клиент для подключения к ManticoreSearch по MySQL-протоколу;
- HTTP API ManticoreSearch;
- Python-скрипт для генерации и загрузки данных;
- PostgreSQL для сравнения полнотекстового поиска;
- текстовые файлы в каталоге `checks/` для сохранения результатов выполнения команд.


## 3. Развёртывание ManticoreSearch

ManticoreSearch был развёрнут в Docker-контейнере. Для этого был подготовлен файл `docker-compose.yml`, в котором описан сервис ManticoreSearch и проброшены необходимые порты:

- `9306` — MySQL-compatible SQL interface;
- `9308` — HTTP API.

Пример структуры сервиса:

```yaml
services:
  manticore:
    image: manticoresearch/manticore:latest
    container_name: manticore
    ports:
      - "9306:9306"
      - "9308:9308"
    ulimits:
      nproc: 65535
      nofile:
        soft: 65535
        hard: 65535
    restart: unless-stopped
```

После запуска контейнера была выполнена проверка подключения двумя способами.

### 3.1. Подключение через MySQL-протокол

Команда:

```bash
mysql -h 127.0.0.1 -P 9306
```

Результат подключения был сохранён в файл:

```text

```

### 3.2. Подключение через HTTP API

Команда:

```bash

```

Результат выполнения также был сохранён в файл:

```text

```

Таким образом было подтверждено, что ManticoreSearch доступен как через SQL-интерфейс, так и через HTTP API.


## 4. Создание RT-индекса

Для хранения каталога товаров был создан real-time индекс `products`.

SQL-запрос:

```sql
CREATE TABLE products (
    title         text,
    description   text,
    category      string,
    brand         string,
    price         float,
    rating        float,
    reviews_count integer,
    in_stock      bool,
    tags          json,
    created_at    timestamp
) morphology='stem_enru' min_word_len='2' html_strip='1';
```

### 4.1. Назначение параметров индекса

Параметр:

```sql
morphology='stem_enru'
```

включает стемминг для английского и русского языков. Это значит, что слова приводятся к условной основе. Например, слова `running`, `runs`, `run` могут рассматриваться как близкие формы одного слова. Для русского языка аналогично могут обрабатываться разные формы одного слова: падежи, числа и другие словоформы.

Параметр:

```sql
min_word_len='2'
```

задаёт минимальную длину слова, которое будет попадать в индекс. В данном случае слова длиной меньше двух символов не индексируются. Это уменьшает размер индекса и помогает отсечь слишком короткие и обычно малополезные токены.

Параметр:

```sql
html_strip='1'
```

включает удаление HTML-тегов из текстовых полей перед индексацией. Это полезно, если описания товаров содержат HTML-разметку, например `<br>`, `<p>`, `<b>` и другие теги.

### 4.2. RT-индекс и plain-индекс

RT-индекс отличается от plain-индекса тем, что позволяет добавлять, обновлять и удалять документы без полной переиндексации. Он больше похож на обычную таблицу, с которой можно работать в режиме реального времени.

Plain-индекс обычно строится заранее из внешнего источника данных. При изменении исходных данных его часто необходимо переиндексировать. Такой подход может быть удобен для статичных или редко изменяемых данных, но хуже подходит для каталога товаров, где цены, наличие, рейтинг и описания могут часто меняться.

Для данной лабораторной работы RT-индекс подходит лучше, так как каталог товаров является динамическим набором данных.

## 6. Полнотекстовый поиск

## 7. Фасетный поиск и агрегации

Фасетный поиск используется в e-commerce для построения фильтров каталога. Например, после поиска по слову `gaming` пользователь может увидеть доступные категории, бренды, диапазоны цен и количество товаров в каждой группе.

### 7.1. Агрегация по категориям

Запрос:

```sql
SELECT category, COUNT(*) AS cnt, AVG(price) AS avg_price
FROM products
WHERE MATCH('gaming')
GROUP BY category
ORDER BY cnt DESC;
```

Результат был сохранён в файл:

```text
checks/facets.txt
```

Запрос показывает, в каких категориях чаще всего встречаются товары по запросу `gaming`, а также среднюю цену товаров в каждой категории.


### 7.2. FACET-запрос

Запрос:

```sql
SELECT id, title, price FROM products WHERE MATCH('gaming')
FACET category ORDER BY COUNT(*) DESC
FACET brand ORDER BY COUNT(*) DESC;
```

Данный запрос одновременно возвращает найденные товары и фасеты по категориям и брендам.

Фасеты особенно полезны в интернет-магазинах, потому что позволяют быстро построить боковую панель фильтров:

- категории;
- бренды;
- цвета;
- размеры;
- диапазоны цен;
- наличие;
- рейтинг.

В отличие от обычного SQL-подхода, поисковый движок изначально оптимизирован под такую задачу: сначала выполняется полнотекстовый поиск, затем по найденному множеству быстро строятся агрегированные фильтры.


## 8. Сравнение с PostgreSQL

Для сравнения был использован PostgreSQL с механизмом полнотекстового поиска `tsvector` и индексом `GIN`.

В PostgreSQL была создана таблица `pg_products`, содержащая те же данные или их подмножество. Затем был добавлен вычисляемый столбец `tsv`:

```sql
ALTER TABLE pg_products ADD COLUMN tsv tsvector
    GENERATED ALWAYS AS (to_tsvector('english', title || ' ' || description)) STORED;
```

После этого был создан GIN-индекс:

```sql
CREATE INDEX idx_tsv ON pg_products USING GIN(tsv);
```

Тестовый запрос:

```sql
SELECT title, ts_rank(tsv, q) AS rank
FROM pg_products, to_tsquery('english', 'wireless & bluetooth & headphones') q
WHERE tsv @@ q
ORDER BY rank DESC
LIMIT 10;
```

Результаты сравнения были сохранены в файл:

```text
checks/pg_vs_manticore.txt
```

|---|---|---|

| Релевантность | Используется BM25 и специализированное ранжирование поискового движка | Используется `ts_rank`, возможностей ранжирования меньше |
| Морфология из коробки | Есть поддержка морфологии и стемминга, в том числе `stem_enru` | Есть словари и конфигурации полнотекстового поиска, но настройка менее удобна для поисковых сценариев |
| Фасетный поиск | Поддерживается напрямую через `FACET` и агрегации | Реализуется через SQL `GROUP BY`, но это менее специализированный сценарий |
| JSON-атрибуты | Можно использовать JSON-атрибуты в документах и фильтровать по ним | JSON/JSONB поддерживается хорошо, особенно с индексами |

| Когда использовать | Когда нужен быстрый поиск по большому количеству текстовых документов | Когда важны транзакции, связи между таблицами и целостность данных |

### 8.2. Вывод по сравнению

ManticoreSearch лучше подходит для задач, где основная нагрузка связана с поиском: поиск по тексту, ранжирование, фильтрация, фасеты, быстрый ответ на пользовательский запрос.

PostgreSQL лучше подходит как основная реляционная база данных, где важны транзакции, связи между сущностями, ограничения целостности и сложная бизнес-логика.

На практике эти системы не заменяют друг друга. Часто PostgreSQL используется как основное хранилище данных, а ManticoreSearch — как отдельный поисковый индекс, куда выгружаются данные, необходимые для быстрого поиска.



## 9. Обновление, удаление и замена документов

В рамках NoSQL-составляющей были продемонстрированы операции `UPDATE`, `DELETE` и `REPLACE`.

### 9.1. UPDATE

Пример обновления рейтинга и цены товара:

```sql
UPDATE products
SET price = 4990.0, rating = 4.9
WHERE id = 1;
```

Проверка результата:

```sql
SELECT id, title, price, rating
FROM products
WHERE id = 1;
```

Результат был сохранён в файл:

```text
checks/update_delete.txt
```

Операция `UPDATE` в ManticoreSearch применяется к атрибутам документа. При этом ManticoreSearch не является полноценной транзакционной СУБД, поэтому его `UPDATE` нельзя считать полным аналогом `UPDATE` в PostgreSQL.


### 9.2. DELETE

Пример удаления документа:

```sql
DELETE FROM products WHERE id = 1;
```

Проверка удаления:

```sql
SELECT id, title
FROM products
WHERE id = 1;
```

Также можно проверить, что документ больше не находится поисковым запросом:

```sql
SELECT id, title
FROM products
WHERE MATCH('wireless bluetooth headphones') AND id = 1;
```

После удаления документ не должен возвращаться в результатах поиска.


### 9.3. REPLACE

Операция `REPLACE` позволяет заменить документ целиком. Если документ с указанным `id` уже существует, он будет перезаписан. Если документа нет, он будет создан.

Пример:

```sql
REPLACE INTO products (
    id, title, description, category, brand,
    price, rating, reviews_count, in_stock, tags, created_at
)
VALUES (
    1,
    'Updated Gaming Laptop',
    'Powerful gaming laptop with dedicated graphics and fast SSD',
    'electronics',
    'GameBox',
    79990.0,
    4.8,
    230,
    1,
    '{"color":"black","type":"gaming","storage":"ssd"}',
    1717000000
);
```

Проверка:

```sql
SELECT id, title, price, rating, tags
FROM products
WHERE id = 1;
```


## 10. Отличие UPDATE в ManticoreSearch от UPDATE в PostgreSQL

В PostgreSQL операция `UPDATE` выполняется в рамках транзакционной модели. Это значит, что можно использовать `BEGIN`, `COMMIT`, `ROLLBACK`, блокировки, ограничения целостности, внешние ключи и другие механизмы ACID.

В ManticoreSearch модель другая. Он в первую очередь является поисковым движком, а не основной транзакционной СУБД. Обновление документов ориентировано на изменение поискового индекса и атрибутов, а не на сложную транзакционную обработку бизнес-данных.

Основные отличия:

| Критерий | ManticoreSearch | PostgreSQL |
|---|---|---|
| Основная роль | Поисковый индекс | Реляционная СУБД |
| Транзакции | Нет полноценных ACID-транзакций | Есть ACID-транзакции |
| UPDATE | Используется для изменения атрибутов документа | Используется для изменения строк таблиц |
| Связи между таблицами | Не основной сценарий | Поддерживаются через внешние ключи |
| Консистентность | В кластере возможна eventual consistency | Строгая транзакционная консистентность |
| Типичные данные | Документы и поисковые атрибуты | Нормализованные бизнес-данные |

Поэтому ManticoreSearch лучше рассматривать как специализированный поисковый слой поверх основной базы данных, а не как полную замену PostgreSQL.

## 13. Итоговый вывод

В ходе лабораторной работы был развёрнут ManticoreSearch и создан real-time индекс для каталога товаров. В индекс было загружено не менее 100 000 документов, после чего были проверены разные виды полнотекстового поиска: базовый поиск, поиск по точной фразе, proximity-поиск, поиск с фильтрацией по атрибутам и поиск по JSON-полю.

Также были рассмотрены фасеты и агрегации, которые особенно полезны для интернет-магазинов, так как позволяют строить фильтры по категориям, брендам и другим характеристикам товаров.

Сравнение с PostgreSQL показало, что PostgreSQL лучше подходит для роли основной транзакционной базы данных, а ManticoreSearch — для роли специализированного поискового движка. ManticoreSearch удобнее использовать там, где важны скорость полнотекстового поиска, релевантность, фасеты и гибкая работа с документами.

Таким образом, ManticoreSearch не следует рассматривать как замену PostgreSQL. Более правильный подход — использовать PostgreSQL как основное хранилище, а ManticoreSearch как отдельный поисковый слой для быстрого и удобного поиска по каталогу товаров.
