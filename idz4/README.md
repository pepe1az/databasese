# Отчёт по выполнению ИДЗ-4

## Шардирование в ClickHouse

## 1. Цель работы

Целью лабораторной работы являлось развёртывание шардированного кластера ClickHouse, изучение работы движка `Distributed`, настройка ключа шардирования и проверка распределения данных между шардами.

В ходе работы необходимо было:

* развернуть ClickHouse-кластер с двумя шардами и двумя репликами на каждом шарде;
* настроить ClickHouse Keeper / ZooKeeper-кворум из трёх узлов;
* создать локальные таблицы на движке `ReplicatedMergeTree`;
* создать распределённую таблицу на движке `Distributed`;
* вставить большой объём тестовых данных через распределённую таблицу;
* проверить распределение данных по шардам;
* выполнить аналитические запросы через `Distributed`;
* рассмотреть особенности `GROUP BY`, `JOIN`, `GLOBAL IN`;
* добавить третий шард и описать особенности ребалансировки данных.


## 2. Топология кластера

Для выполнения работы был развёрнут ClickHouse-кластер в Docker Compose.

Итоговая топология:

| Узел       | Шард |    Реплика |
| ---------- | ---: | ---------: |
| `ch-s1-r1` | `01` | `replica1` |
| `ch-s1-r2` | `01` | `replica2` |
| `ch-s2-r1` | `02` | `replica1` |
| `ch-s2-r2` | `02` | `replica2` |

Также были развёрнуты три узла ClickHouse Keeper:

| Узел      | Назначение         |
| --------- | ------------------ |
| `keeper1` | первый узел Keeper |
| `keeper2` | второй узел Keeper |
| `keeper3` | третий узел Keeper |

Keeper использовался для координации репликации таблиц `ReplicatedMergeTree`. Три узла Keeper позволяют сохранять кворум при отказе одного узла, так как для работы кворума достаточно большинства — двух узлов из трёх.


## 3. Настройка кластера 2x2

В конфигурации `remote_servers` был описан кластер `cluster_2x2`.

Пример конфигурации:

```xml
<remote_servers>
    <cluster_2x2>
        <shard>
            <replica>
                <host>ch-s1-r1</host>
                <port>9000</port>
            </replica>
            <replica>
                <host>ch-s1-r2</host>
                <port>9000</port>
            </replica>
        </shard>

        <shard>
            <replica>
                <host>ch-s2-r1</host>
                <port>9000</port>
            </replica>
            <replica>
                <host>ch-s2-r2</host>
                <port>9000</port>

```

Для каждого узла были настроены макросы `{shard}` и `{replica}`.

Пример макросов для узла `ch-s1-r1`:

Для остальных узлов значения макросов были изменены в соответствии с их шардом и репликой:

| Узел       | `{shard}` | `{replica}` |

| `ch-s1-r2` | `01`      | `replica2`  |
| `ch-s2-r1` | `02`      | `replica1`  |

## 4. Создание локальной таблицы

В качестве предметной области использовались события пользовательской аналитики, то есть clickstream-данные.

Была создана локальная таблица `events_local` на всех узлах кластера.

SQL-запрос:

```sql
CREATE TABLE events_local ON CLUSTER 'cluster_2x2'
(
    event_date  Date,
    event_time  DateTime,
    user_id     UInt64,
    session_id  String,
    event_type  LowCardinality(String),
    page_url    String,
    duration_ms UInt32
)
ENGINE = ReplicatedMergeTree(
    '/clickhouse/tables/{shard}/events_local',
    '{replica}'
)
PARTITION BY toYYYYMM(event_date)
ORDER BY (user_id, event_time);
```

Таблица использует движок `ReplicatedMergeTree`.

Путь в Keeper:

```text
/clickhouse/tables/{shard}/events_local
```

указывает, что для каждого шарда создаётся свой путь репликации.

Это важно: репликация происходит внутри шарда, а не между всеми узлами сразу. То есть:

* `ch-s1-r1` реплицируется с `ch-s1-r2`;
* `ch-s2-r1` реплицируется с `ch-s2-r2`.

Макрос `{replica}` задаёт имя конкретной реплики внутри шарда.


## 5. Создание распределённой таблицы

После создания локальной таблицы была создана распределённая таблица `events_distributed`.

SQL-запрос:

```sql
CREATE TABLE events_distributed ON CLUSTER 'cluster_2x2'
AS events_local
ENGINE = Distributed(
    'cluster_2x2',
    default,
    events_local,
    xxHash64(user_id)
);
```

Таблица `events_distributed` не хранит данные самостоятельно. Она является логическим слоем поверх локальных таблиц `events_local`.

При вставке в `events_distributed` ClickHouse вычисляет выражение шардирования:

```sql
xxHash64(user_id)
```

и на его основе выбирает нужный шард.


## 6. Обоснование ключа шардирования

В качестве ключа шардирования был выбран:

```sql
xxHash64(user_id)
```

Такой выбор является логичным для clickstream-данных, потому что большинство аналитических запросов часто группируются или фильтруются по пользователю.

Преимущества шардирования по `user_id`:

* все события одного пользователя попадают на один и тот же шард;
* запросы вида `GROUP BY user_id` выполняются эффективнее;
* уменьшается необходимость пересылать данные одного пользователя между шардами;
* распределение получается достаточно равномерным, если пользователей много.

Вариант с `event_date` хуже, потому что данные могут распределяться неравномерно. Например, если большая часть событий относится к одному дню или месяцу, один шард может получить намного больше данных, чем другой.

Вариант с `rand()` тоже не подходит, потому что события одного пользователя будут случайно разбросаны по разным шардам. Это усложнит агрегации по пользователям и приведёт к дополнительной пересылке данных между узлами.

Таким образом, `xxHash64(user_id)` является хорошим компромиссом между равномерностью распределения и эффективностью аналитических запросов.


## 7. Наполнение таблицы тестовыми данными

Для проверки работы шардирования было вставлено не менее 2 000 000 строк через распределённую таблицу `events_distributed`.

Пример SQL-запроса для вставки:

```sql
INSERT INTO events_distributed
SELECT
    today() - number % 30 AS event_date,
    now() - number % 100000 AS event_time,
    number % 500000 AS user_id,
    concat('session_', toString(number % 100000)) AS session_id,
    ['view', 'click', 'scroll', 'purchase', 'login'][number % 5 + 1] AS event_type,
    concat('/page/', toString(number % 1000)) AS page_url,
    toUInt32(number % 30000) AS duration_ms
FROM numbers(2000000);
```

Данные вставлялись именно через `events_distributed`, чтобы ClickHouse самостоятельно распределил строки между шардами согласно ключу шардирования.

## 8. Проверка распределения данных по шардам

После вставки была выполнена проверка количества строк в локальной таблице на каждом узле.

* `ch-s1-r1` и `ch-s1-r2` должны содержать одинаковые данные;

## 9. Проверка размещения данных одного пользователя

Так как ключом шардирования является `xxHash64(user_id)`, все события одного `user_id` должны попадать на один и тот же шард.

Для проверки можно использовать запросы к локальным таблицам на разных шардах. Например, выбрать конкретного пользователя и проверить его наличие:

```sql
SELECT
    hostName(),
    count()
FROM events_local
WHERE user_id = 12345
GROUP BY hostName();
```

Ожидаемый результат:

* данные пользователя находятся только на одном шарде;
* при этом они присутствуют на обеих репликах этого шарда.

Это подтверждает, что шардирование по `user_id` работает предсказуемо.


## 10. Запросы через Distributed

### 10.1. Глобальный COUNT

Сначала был выполнен глобальный подсчёт строк через распределённую таблицу:

```sql
SELECT count()
FROM events_distributed;
```

Также была проверена сумма локальных строк по шардам.

Ожидаемый результат:

```text
2000000
```

Результат через `events_distributed` совпал с суммой строк в локальных таблицах по шардам.

Это подтверждает, что распределённая таблица корректно читает данные со всех шардов.


### 10.2. GROUP BY по шардированному ключу

Был выполнен запрос для получения топ-10 пользователей по числу событий:

```sql
SELECT
    user_id,
    count() AS events_count
FROM events_distributed
GROUP BY user_id
ORDER BY events_count DESC
LIMIT 10;
```

Этот запрос является эффективным, потому что `user_id` используется как ключ шардирования.

Это означает, что все события одного пользователя находятся на одном шарде. ClickHouse может выполнить локальную агрегацию на шардах, а затем объединить уже частично агрегированные результаты.


### 10.3. GROUP BY без шардированного ключа

Также был выполнен запрос для получения топ-10 страниц по числу посещений:

```sql
SELECT
    page_url,
    count() AS visits
FROM events_distributed
GROUP BY page_url
ORDER BY visits DESC
LIMIT 10;
```

В этом случае группировка выполняется по `page_url`, который не является ключом шардирования.

Это значит, что события одной и той же страницы могут находиться на разных шардах. Поэтому ClickHouse вынужден собирать промежуточные результаты с разных шардов и объединять их на инициирующем узле.

Такой запрос потенциально менее эффективен, чем `GROUP BY user_id`, потому что требует дополнительного этапа объединения данных между шардами.


## 11. JOIN со справочной таблицей

Для проверки `JOIN` была создана справочная таблица `user_dict`.

DDL таблицы:

```sql
CREATE TABLE user_dict ON CLUSTER 'cluster_2x2'
(
    user_id UInt64,
    name String,
    segment LowCardinality(String)
)
ENGINE = ReplicatedMergeTree(
    '/clickhouse/tables/{shard}/user_dict',
    '{replica}'
)
ORDER BY user_id;
```

Пример наполнения справочника:

```sql
INSERT INTO user_dict
SELECT
    number AS user_id,
    concat('user_', toString(number)) AS name,
    ['free', 'premium', 'enterprise'][number % 3 + 1] AS segment
FROM numbers(500000);
```

После этого был выполнен запрос с `JOIN`:

```sql
SELECT
    d.segment,
    count() AS events_count
FROM events_distributed AS e
JOIN user_dict AS d
ON e.user_id = d.user_id
GROUP BY d.segment
ORDER BY events_count DESC;
```

При работе с распределёнными таблицами `JOIN` может быть дорогой операцией. Если справочная таблица находится не на тех же шардах или не распределена тем же способом, ClickHouse может выполнять пересылку данных между шардами.

Один из способов решения проблемы — использовать `GLOBAL JOIN` или `GLOBAL IN`. В этом случае небольшая справочная таблица передаётся на каждый удалённый узел, после чего соединение выполняется локально.

Пример:

```sql
SELECT
    segment,
    count() AS events_count
FROM events_distributed
WHERE user_id GLOBAL IN
(
    SELECT user_id
    FROM user_dict
    WHERE segment = 'premium'
)
GROUP BY segment;
```

Однако `GLOBAL`-операции нужно использовать аккуратно. Они хорошо подходят для небольших справочников, но для больших таблиц могут привести к значительной сетевой нагрузке.

## 13. Что происходит со старыми данными при добавлении шарда

При добавлении нового шарда ClickHouse не переносит старые данные автоматически.

Это важный момент: `Distributed`-таблица определяет, куда отправлять новые вставки, но она не выполняет автоматическую ребалансировку уже существующих данных.

То есть после добавления третьего шарда:

* старые данные остаются на первых двух шардах;
* новые данные начинают распределяться уже с учётом третьего шарда;
* распределение становится неравномерным до тех пор, пока не будет выполнена ручная ребалансировка.


## 14. Подход к ребалансировке

Ребалансировку можно выполнить вручную.

Общий подход:

1. Создать новую распределённую таблицу с актуальной конфигурацией шардов.
2. Переложить данные из старой таблицы в новую через `INSERT ... SELECT`.
3. Убедиться, что данные распределились по новому ключу шардирования.
4. Проверить количество строк и контрольные суммы.
5. Переключить приложение на новую таблицу.
6. Удалить старые данные после проверки.

Примерный вариант:

```sql
INSERT INTO events_distributed_new
SELECT *
FROM events_distributed_old;
```

Также возможен более аккуратный подход:

* переносить данные по партициям;
* временно остановить запись;
* использовать промежуточные таблицы;
* проверять `count()`, `sum()`, `uniq()` и контрольные агрегаты;
* после проверки выполнить переименование таблиц.

Ребалансировка в ClickHouse требует отдельного планирования, потому что при больших объёмах данных она может создать серьёзную нагрузку на сеть, CPU и диски.

* `GROUP BY page_url` требует объединения данных с разных шардов;
* `JOIN` в распределённой среде требует аккуратного подхода, особенно если справочник большой или не совпадает по схеме шардирования.

Также было показано, что при добавлении нового шарда ClickHouse не переносит старые данные автоматически. Новые данные начинают распределяться с учётом обновлённой конфигурации, но старые остаются на прежних шардах. Для равномерного распределения требуется отдельная процедура ребалансировки.

Таким образом, лабораторная работа позволила изучить базовые принципы шардирования в ClickHouse, работу `Distributed`-таблиц, влияние ключа шардирования на запросы и особенности масштабирования кластера.
